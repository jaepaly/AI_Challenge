# W5 무중단 리허설 — 폴링 사양과 런북

심사 기간 **2026-09-07 11:00 ~ 2026-09-11 23:59** 동안 배포 URL이 죽으면 결격이다.
이 문서는 무엇을 폴링하고, 무엇이 울리면 무엇을 하는지를 정한다.

C 트랙 항목(README §5-C)이나 8/19 기준 C 부재로 D가 인수했다.

---

## 1. 폴링 대상은 둘이다

| 엔드포인트 | 답하는 질문 | 상류 호출 |
|---|---|---|
| `/api/build` | 서버가 살아 있나 + **어느 커밋인가** | 0 |
| `/api/readiness` | 그 커밋이 **실제로 답을 내나** | 0 |

### 왜 하나로 안 합치나

`/api/build`는 배포 신선도 판별에 이미 쓰이고 있다(README §6-5). 준비도 판정이
그 계약을 흔들면 안 된다. 그리고 두 신호는 **다른 장애를 잡는다**:

```
배포 롤백/지연   /api/build 의 shortSha 가 main HEAD 와 다름
프리뷰 오인      /api/build 의 branch 가 main 이 아님
제품 기능 정지   /api/readiness 가 503        ← build 는 내내 200
```

### `/api/build`만으로는 못 보는 구간이 실재한다

스냅숏 카드의 `verified_at`이 `2026-08-09`이고 신선도 게이트가 30일이라
**2026-09-09부터 화면이 "산정 불가"가 된다**(#54 실측):

```
심사일        경과일   화면          /api/build
2026-09-07     29일   calculated    200 · 올바른 sha
2026-09-08     30일   calculated    200 · 올바른 sha
2026-09-09     31일   blocked       200 · 올바른 sha   ← 서버는 멀쩡, 제품이 죽음
2026-09-10     32일   blocked       200 · 올바른 sha
2026-09-11     33일   blocked       200 · 올바른 sha
```

**심사 창의 60%다.** sha만 보는 폴링은 사흘 동안 초록을 보고한다.

### ⚠ `/api/ingest/health`는 폴링하지 않는다

인증이 없고 히트마다 상류로 나간다. 무인 폴링을 걸면 **우리 API 키의 레이트리밋
슬롯을 우리 감시자가 소모**하고, 정작 심사위원 업로드가 429로 막힌다.

토큰 과금은 없다(`/v1/models`는 목록 조회다). **비용 항목이 아니라 가용성 항목**이다.
60초 메모이제이션을 걸어 뒀지만 그건 외부인이 두드릴 때의 방어이지 폴링 허가가 아니다.

## 2. 폴링 사양

```bash
# 5분 간격. 심사 기간에는 2분.
curl -fsS "$URL/api/build"      | jq -e '.branch == "main"'
curl -fsS "$URL/api/readiness"  | jq -e '.ok == true'
```

`/api/readiness`는 준비되지 않았을 때 **503**을 준다. `curl -f`가 그대로 실패한다.

| 신호 | 임계 | 뜻 |
|---|---|---|
| HTTP != 200 | 2회 연속 | 배포 다운 — 즉시 대응 |
| `.branch != "main"` | 1회 | 프리뷰를 프로덕션으로 착각 중 |
| `.shortSha != main HEAD` | 1회 | 배포가 뒤처짐 |
| `.ok == false` | 1회 | **제품이 답을 못 냄** — 아래 §4 |
| `.daysUntilBlocked <= 7` | 1회 | **예보 경보** — 아직 초록이지만 곧 뒤집힌다 |

마지막 줄이 이 설계의 핵심이다. `daysUntilBlocked`가 있으면 **9/9 정지를 8/19에
알 수 있다.** #54는 사람이 README 한 줄을 읽고 손으로 계산해 찾았다. 다음부터는
폴링이 먼저 운다.

## 3. 리허설 — 검사가 진짜인지 먼저 깨 본다

**초록을 확인하는 것은 리허설이 아니다.** 검사가 실제로 발화하는지를 본다.

```bash
# ① 준비도 검사가 심사 구간에서 실제로 빨간불이 되는가
curl -s "$URL/api/readiness?at=2026-09-09T00:00:00%2B09:00" | jq '.ok, .degraded'
#   → false, ["한국투자","메리츠"]   ... true 가 나오면 이 검사는 가짜다

# ② 심사 첫날은 초록인가 (거짓 경보가 아닌지)
curl -s "$URL/api/readiness?at=2026-09-07T00:00:00%2B09:00" | jq '.ok'
#   → true

# ③ 예보가 도는가
curl -s "$URL/api/readiness" | jq '.nextBlockedAt, .daysUntilBlocked'
#   → "2026-09-09", 21

# ④ 배포 신선도
curl -s "$URL/api/build" | jq -r '.shortSha, .branch'
git rev-parse --short main
```

⚠ `?at=`은 **리허설 전용**이다. 무인 폴링에 붙이면 감시가 아니라 시뮬레이션이 된다.

### 시간대 — 판정은 KST로 한다

화면의 `asOf`는 브라우저 로컬 날짜다. 심사위원은 한국에 있고 서버(Vercel)는 UTC다.
**매일 9시간 동안 둘의 날짜가 다르다**:

```
2026-09-08T15:30Z  →  서버 UTC 9/8 (fresh)  /  심사위원 KST 9/9 (blocked)
```

UTC로 판정하면 그 9시간을 놓치고, **놓치는 방향이 낙관**이다. 그래서
`/api/readiness`는 KST로 판정한다.

## 4. `.ok == false`가 울렸을 때

### 원인이 카드 만료(STALE)라면 — `verified_at`을 그냥 올리지 않는다

`verified_at`은 *"이 날짜에 사람이 원문과 대조했다"*는 뜻이다. 대조 없이 날짜만
올리는 것은 이 저장소가 막으려는 바로 그 거짓이다(#51에서 근거가 예시였던 것과 같은 종류).

**아래 §5 절차를 밟은 뒤에** 올린다.

### 원인이 배포라면

```bash
gh run list --workflow=deploy --limit 3     # 배포 워크플로 상태
curl -s "$URL/api/build" | jq              # 실제로 뜬 커밋
```

## 5. 9/6 전 카드 재검증 절차 (D + A 공동)

심사 시작 전날에 돌린다. **#52 이후 기계 몫이 커져서 30분이면 끝난다.**

### ① 기계 — 3검사 (자동)

```bash
cd services/ingest && python -m unittest discover -s tests
```

이 셋이 재검증의 뼈대다:

| 검사 | 확인하는 것 |
|---|---|
| `test_snapshot_evidence` | 좌표·sha·인용문이 원문과 글자 단위로 일치 |
| `test_snapshot_card_validates` | 카드가 우리 Pydantic을 통과 |
| `test_snapshot_evidence_normativity` | 근거가 **예시 구간과 겹치지 않음** |

`test_terms_worktree_bytes`도 같이 돈다 — 작업트리 CRLF 오염을 잡는다.
**유료 실행 전에 반드시 통과해야 한다**(#49에서 실제 사고가 났다).

### ② 사람 — 1확인

기계가 확인 못 하는 것은 하나뿐이다:

> **원문이 개정됐는가?**

각 회사 페이지에서 약관 파일을 다시 받아 `git hash-object`로 대조한다.

```bash
git -c core.quotepath=false ls-files -- data/terms | while read -r f; do
  printf '%s  %s\n' "$(git hash-object "$f")" "$f"
done
```

새로 받은 파일의 해시가 다르면 **개정된 것**이다. 그때는 날짜를 올리는 게 아니라
근거 좌표를 다시 뽑아야 한다(#52와 같은 작업).

### ③ 반영

개정이 없으면 `snapshot.ts`의 `verified_at`을 **재검증한 날짜**로 올린다.
9/6로 올리면 10/6까지 유효해 심사 창(9/11)을 덮는다.

```bash
curl -s "$URL/api/readiness?at=2026-09-11T23:59:00%2B09:00" | jq '.ok'   # → true 확인
```

### ④ 잔액

README §8 하드 가드 — **9/6에 Anthropic 잔액 확인 + 여유분 충전.**

⚠ 무엇이 죽는지 정확히 적는다. **심사 URL은 크레딧이 0이어도 안 죽는다** —
`/api/ingest`가 404라 배포본은 런타임 API를 한 번도 호출하지 않는다(2026-08-23 실측,
README §8). 크레딧이 필요한 것은 **저장소 안의 유료 종단**(`services/ingest`
2패스 카드 생성, `#68` B-1)이고, 그건 심사 기간에 우리가 돌릴 때만 쓴다.

업로드 라우트가 생기면 이 항목의 성격이 바뀐다 — 그때는 심사 URL이 크레딧에
의존하게 되므로 이 문단을 함께 고친다.

### ⑤ 브라우저 확인

첨부2 §5 ③절이 이 항목을 근거로 브라우저 범위를 적는다. **잰 것만 적기 위해
여기서 잰다.**

지금까지 확인된 것은 하나뿐이다:

```
2026-08-23  Chromium 148 / 375×812
  documentElement.scrollWidth 375 = innerWidth 375     페이지 가로 스크롤 없음
  콘솔 오류 0건
  넓은 표(내용 560px)는 overflow-x:auto 컨테이너에서 자체 스크롤
  scrollLeft 최대 267 = 560 − 293                      끝까지 도달, 잘리지 않음
```

9/6에 확인할 것:

- [ ] **파이어폭스** — 데스크톱 폭. 계산·배너·근거 패널이 뜨는지
- [ ] **사파리** — 있으면. 없으면 *"확인하지 않았다"*로 §5에 남긴다
- [ ] **엣지** — Chromium 계열이라 우선순위 낮음
- [ ] **375px 재확인** — 카드 셋 각각에서 가로 스크롤 없음

측정 방법(브라우저 콘솔):

```js
({ vw: innerWidth, doc: document.documentElement.scrollWidth,
   overflow: document.documentElement.scrollWidth > innerWidth })
```

⚠ **연 브라우저만 §5에 적는다.** 열지 못한 것은 *"동작한다"*가 아니라
*"확인하지 않았다"*로 적는다 — 심사자가 그 브라우저로 열었다가 깨지면 §5 전체의
신뢰가 흔들린다(`#73` 리뷰, A).

## 6. 알려진 한계

- **인스턴스 간 상태 없음.** `/api/ingest/health`의 60초 메모이제이션은 서버리스
  인스턴스마다 독립이다. N개면 분당 N회까지 상류로 나간다(#31 P2-a와 같은 한계).
- **`/api/readiness`는 스냅숏 카드만 본다.** 인제스트 업로드 경로의 건강은 안 본다.
  업로드 라우트가 생기면 별도 신호가 필요하다.
- **`?at=` 예보는 120일까지만 본다.** 그 밖은 `null`이다 — 없는 날짜를 지어내지 않는다.
- **draft 카드는 degraded로 세지 않는다.** 설계상 항상 참고 모드라 세면 상시
  빨간불이 되고 진짜 신호가 묻힌다. 하한가형 카드가 여기 해당한다.
