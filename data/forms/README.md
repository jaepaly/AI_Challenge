# 공모전 공식 제출 양식 (첨부1·첨부2)

주최측이 배포한 `.hwpx` 원본이다. **절 제목과 순서가 고정**이고, README §5-D가 적어둔 대로
**작년 유일한 부적격 사유가 "양식 미작성"**이다. 그래서 원본 바이트를 저장소에 둔다 —
약관(`data/terms/`)과 같은 취급이다.

둘 다 `504b0304`(PK zip) 로 시작하는 정상 hwpx다 — hwpx 는 XML 을 담은 zip 이고,
본문은 `Contents/section0.xml` 의 `<hp:t>` 에 있다.

확인:

```bash
git -c core.quotepath=false ls-files -- data/forms | while read -r f; do
  printf '%s  %s\n' "$(git hash-object "$f")" "$f"
done
```

⚠ **양식이 갱신되면 sha 가 바뀐다.** 주최측이 중간에 양식을 고치는 경우가 있으므로,
9/7 제출 전에 다시 받아 대조한다. `test_submission_forms.py` 가 절 구조까지 같이 본다.

## 첨부2 — 기능명세서 (5절 전부 필수)

| 절 | 제목 | 요구사항 |
|---|---|---|
| 1 | MVP 구현 범위 | 구현한 범위만. **미구현·향후 예정 기능은 제외** |
| 2 | 주요 기능 목록 | **실제 동작하는** 기능 단위. `기능명 / 기능 설명 / 관련 화면 / 구현 상태` |
| 3 | 사용자 이용 흐름 | **배포 URL 접속 후** 주요 기능 사용 순서 |
| 4 | AI 및 데이터 처리 방식 | AI 역할 · 사용/입출력 데이터 · (필요시) 개인정보·민감정보 처리 여부 |
| 5 | MVP 검증 방법 | 심사자가 **배포 URL에서** 확인하는 절차 · 계정/샘플 입력값/예상 결과 · 실행환경·브라우저 제한 · **MVP 단계의 제한사항** |

### 이 양식이 우리 저장소에 요구하는 것

- **§2 "구현 상태"** — 기능마다 상태를 적어야 한다. "예정"을 적을 칸이 아니라 §1이
  *"미구현 또는 향후 구현 예정 기능은 제외"*라고 못 박았으므로, **적는 순간 동작해야 한다.**
- **§3·§5가 배포 URL을 전제**로 쓰인다. 문서 두 개가 URL 없이는 성립하지 않는다 —
  배포는 부록이 아니다.
- **§5 "MVP 단계의 제한사항"** — 우리가 이슈·주석·테스트에 정직하게 기록해 온 한계들이
  그대로 들어갈 자리다(`day_counting` 미검증, 대주 카드 미구분, `replay` 미덮임 등).
  숨길 칸이 아니라 **적으라고 만들어 둔 칸**이다.

⚠ **본문은 W5(8/25~)에 쓴다.** §1·§2가 "실제 동작하는 것만"을 요구하므로 8월에 쓰면
9월에 다시 쓴다(README §5-D).
