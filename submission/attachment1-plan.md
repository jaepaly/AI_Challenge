## 2. 아이디어 기획 핵심내용(요약)*

- **무엇을 하는가** — 증권사 신용거래설명서에 적힌 반대매매 조건을 읽어, *"내 주식이 얼마까지 떨어지면 강제로 팔리는가"* 를 **가격 한 줄(임계가)** 과 **수량**으로 환산해 보여준다.
- **왜 지금인가** — 담보부족은 **통보를 받은 뒤가 아니라 담보비율이 무너진 그 순간에 이미 결정**된다. 통보 시점에 남는 선택지는 입금·상환·자발적 매도뿐이고, 그때 계산할 시간은 없다.
- **핵심 설계 — 역할을 나눈다**
  - **생성형 AI는 약관을 읽고 인용만 한다.** 수치를 만들지 않고, 산식을 쓰지 않는다.
  - **계산은 결정론 엔진이 한다.** 같은 입력에 항상 같은 출력이고, 검증 가능하다.
  - 이 경계는 선언이 아니라 **검사로 강제**한다 — 출력에 산식·계산이 섞이면 카드 전체를 거부한다.
- **모든 수치에 근거 좌표를 붙인다** — 원문 파일의 문자 구간(`char_start`/`char_end`), 평탄화 텍스트의 SHA-256, 그리고 인용문 자체. **좌표를 못 찾으면 그 카드를 통째로 거부한다.**
- **모르는 것을 모른다고 말한다** — 세 가지 게이트가 *"계산하지 않음"* 을 선택한다.
  - **신선도** — 검증일로부터 30일이 지난 조건카드는 수량을 내지 않는다.
  - **유지비율 정합** — 카드가 이 계좌에 대해 비율을 하나로 정하지 못하면 수량을 내지 않는다.
  - **인용 거리** — 비율을 가르는 축(상품·종목군)이 인용 스팬 밖에 있는 문서는 **처리 자체를 거부**한다.
- **결과물** — 배포된 웹 화면(https://marginguard-web.vercel.app/). 계좌 연동·회원가입 없이 가상 계좌로 즉시 확인할 수 있다.

## 3. 문제 정의 및 제안 배경*

### 3-1. 문제 — 조건은 공개돼 있는데, 내 숫자로 번역돼 있지 않다

신용거래 약관은 전부 공개돼 있다. 문제는 **그것이 개인의 계좌 숫자로 번역되지 않는다**는 것이다. 우리가 증권사 7곳의 원문을 직접 받아 대조한 결과가 그 이유를 보여준다.

| 회사 | 산정 기준가(h) | 유지비율(r) |
|---|---|---|
| 한국투자 | 전일종가 −15% | 융자 140% · 대주 120% · 대주전용계좌 105% |
| 메리츠 | 전일종가 −20% | 융자 A∙B군 140% / C∙D군 150% · 대주 A∙B군 120% |
| 삼성 | 전일종가 기준 **종목등급별** S·A 85% / B 이하 80% | — |
| 신한 | 하한가 등 | 105% / 120% / 140% / 해외담보 170% |
| 미래에셋 | 전일종가 −15~30% 범위 | 140% / 145% / 120% / 105% |
| 키움 | 미수 하한가(−30%) / 신용 −15% | — |
| 유진 | **하한가** | — |

*(출처: `data/terms/README.md` — 파일별 원본 URL·심사필 번호·SHA-256·수집일 기록)*

**같은 −10% 하락이 회사마다 다른 결과를 낸다.** 우리 엔진으로 같은 계좌(1,000주 × 8,100원, 융자 600만원)를 돌리면 강제처분 수량이 이렇게 갈린다:

```
한국투자   195주      메리츠   309주      하한가형   전량 1,000주
```

세 값의 담보부족액은 **300,000원으로 동일**하다. 갈리는 것은 오직 산정 기준가 h다.

### 3-2. 더 어려운 문제 — 원문 자체가 한 값을 가리키지 않는다

읽기 어려운 정도가 아니라, **같은 상품이 한 문서 안에서 두 비율을 갖는다.**

메리츠 원문에는 담보유지비율 표가 둘 있고, `신용거래대주`가 한 표에서 **105%**, 다른 표에서 **120%** 다. 어느 쪽이 적용되는지는 **표 밖의 문장**이 정한다.

```
구분 담보유지비율 / 신용거래대주 A∙B군 105%
구분 담보유지비율 / 신용거래융자 기본형∙투자형 A∙B군 140% C∙D군 150% / 신용거래대주 A∙B군 120%
```

*(원문: `services/ingest/benchmarks/results/raw_pdf_document.json` `documents[0]` = `메리츠_신용거래설명서_20250421.pdf`)*

**이것이 "AI로 약관을 읽는" 서비스가 조용히 틀리는 자리다.** 그럴듯한 숫자 하나를 골라 내면 사용자는 그것이 근거 있는 값인지 알 수 없다. 우리는 이런 문서를 **거부한다**(§4-3).

### 3-3. 우리가 직접 빠졌던 함정 — 미수와 신용은 다르다

초기 수집에서 키움 문서의 반대매매 조항을 **신용 근거로 분류했다가 정정**했다. 실제로는 *"미수 반대매매 대상 종목이 거래정지된 특수상황"* 조항이었다.

같은 "반대매매"라는 말이 **미수(결제 부족)** 와 **신용(담보 부족)** 두 채널에서 다른 규칙으로 쓰인다. 사람이 읽어도 틀리는 자리이므로, **LLM에게 판단시키지 않고 인용 스팬 안에서 상품이 특정되는지를 기계가 본다.**

### 3-4. 대상 고객과 채널

**대상 — 신용거래 이용 개인투자자, 특히 처음 쓰는 사람.** 신용거래는 진입이 쉽고(HTS에서 몇 번의 클릭), 조건은 약관에 있으며, 결과는 통보 후 되돌릴 수 없다. **쉬움과 되돌릴 수 없음 사이의 간격**이 가장 큰 집단이다.

**채널 — 모바일 웹.** 이유 셋:

1. **설치·가입·연동이 없어야 한다.** 담보부족을 걱정하는 사람에게 앱 설치와 계좌 연동을 요구하면 그 시점에 이탈한다. 배포 URL을 열면 첫 화면에서 바로 숫자가 나온다.
2. **개인정보를 받지 않는다.** 계산에 필요한 것은 보유수량·전일종가·융자금뿐이고 전부 화면 안에 있다. 서버로 보내지 않는다 — **계산이 브라우저에서 돈다.**
3. **증권사 앱 안에서는 만들 수 없는 화면이다.** 자사 조건만 보여줄 수 있고, *"같은 부족액인데 우리는 전량, 옆 회사는 195주"* 를 나란히 놓을 수 없다.

## 4. 서비스 컨셉 및 차별성*

### 핵심 컨셉 — "약관이 정한 그대로, 내 계좌의 한 줄로"

화면 중앙에 슬라이더가 하나 있다. 주가를 끌어내리면 **임계가**에서 색이 바뀌고, 그 아래로는 **담보부족액 · 강제처분 수량 · 해소 경로 네 가지**가 즉시 갱신된다. 조작하는 것은 **가격 슬라이더 · 카드 선택 · 7월 연쇄 재현 버튼** 셋뿐이다.

### 4-1. 차별성 ① — 계산은 AI가 하지 않는다

생성형 AI 금융 서비스가 신뢰를 잃는 가장 흔한 경로는 **모델이 숫자를 만들어 내는 것**이다. 우리는 그 경로를 **구조적으로 닫았다.**

```
LLM 이 하는 것      약관을 읽고, 해당 문장을 인용하고, 그 좌표를 남긴다
LLM 이 못 하는 것   계산 · 산식 작성 · 좌표 자가보고 · 문서 버전 생성
```

강제 수단은 문서가 아니라 **검사**다. 인제스트 출력에 산식·계산 흔적이 섞이면 **카드 전체를 거부**한다(4중 방어 ④). 반대매매 수량은 엔진이 정수 스케일로만 계산한다:

```
담보부족액   D = rL − V
계수         k = r(1−h) − 1
처분 수량    n = ⌈D / (P_prev · k)⌉         k ≤ 0 이면 전량(FULL)
```

### 4-2. 차별성 ② — 모든 수치에 근거 좌표가 붙는다

화면의 모든 비율·기준가는 **원문의 어느 위치에서 왔는지**를 함께 낸다.

```
인용문        "담보유지 비율 융자 융자금의 140%"
문자 좌표     char_start / char_end
문서 해시     flattened_sha256   (원문이 바뀌면 좌표가 무효가 된다)
심사필 번호   제2026-0265호
```

이 좌표는 **선언이 아니라 검사로 지켜진다.** 저장소의 검사가 매번 원문을 다시 파싱해 기록된 해시·좌표·인용문을 대조한다. 실제로 이 검사가 두 번 작동했다:

- 근거로 적힌 아홉 구간 중 넷이 **조항이 아니라 계산 예시**를 가리키고 있던 것을 잡아냈다.
- 2026-08-23 원문 추출기(pypdf) 패치 릴리스가 텍스트 결합 방식을 바꾸자 **9개 좌표가 동시에 무효**가 되는 것을 즉시 잡아냈다. 그래서 추출기를 정확 버전으로 고정한다.

**"근거를 보여준다"고 말하는 것과, 근거가 어긋나면 빨간불이 켜지게 만들어 두는 것은 다르다.**

### 4-3. 차별성 ③ — 모르는 것을 모른다고 말한다

대부분의 서비스는 **답을 내는 쪽으로** 기울어 있다. 우리는 세 자리에서 **계산하지 않기를 선택**한다.

| 게이트 | 언제 막나 | 화면이 하는 말 |
|---|---|---|
| **신선도** | 카드 검증일로부터 30일 초과 | *"이 카드는 재검증이 필요합니다 — 낡은 값을 정식 산출로 내지 않습니다"* |
| **유지비율 정합** | 카드가 이 계좌에 대해 비율을 하나로 못 정함 | 두 값을 **함께** 보여주고, 어느 쪽이 맞는지는 말하지 않는다 |
| **인용 거리** | 비율을 가르는 축이 인용 스팬 밖 | 그 문서를 **지원 범위에서 제외**한다 |

⚠ **막는 것과 가리는 것은 다르다.** 수량을 막는 화면에서도 **근거는 계속 보여준다** — 재검증하러 가려면 어느 판본의 어느 문장인지가 오히려 더 필요하다.

### 4-4. 차별성 ④ — 회사를 비교하되, 우열을 말하지 않는다

같은 계좌·같은 부족액에 **회사 조건만 갈아 끼운** 결과를 나란히 놓는다(195 / 309 / 전량). 이것은 *"어느 증권사가 좋다"* 가 아니라 **"조건이 이만큼 다르다"** 를 보이기 위한 것이고, 화면은 우열 표시를 하지 않는다.

### 4-5. 표시 규약 — 안전 여유를 먼저, 임계점을 나중에

같은 정보라도 *"임계가까지 −16%"* 를 먼저 보여주면 여유를 읽고, *"8,400원에 반대매매"* 를 먼저 보여주면 공포를 읽는다. **안전 여유를 먼저 놓는다.** 겁을 팔지 않는 것이 이 제품의 규율이다.

⚠ 표시 담보비율은 **내림**한다(120.5% → 120%). 엔진 재현값은 사사오입이라 둘이 다를 수 있고, 화면은 **사용자에게 불리한 쪽**으로 반올림한다.

## 5. 활용 데이터 및 생성형 AI 모델 적용 방안*

### 5-1. 데이터 — 증권사 신용거래설명서 원문 7종

| 파일 | 심사필 번호 | 형식 |
|---|---|---|
| 한국투자_신용거래설명서_20260707 | 심사필 제2026-0265호 | HTML |
| 메리츠_신용거래설명서_20250421 | 심의필 제25-125호 | PDF |
| 삼성_신용거래핵심설명서_20240822 | 검토필 제24-0104호 | PDF |
| 신한_신용거래설명서_20260330 | 검토필 26-00486-511 | PDF |
| 키움_국내주식핵심설명서_20260612 | 검토필 제26-0363호 | PDF |
| 미래에셋_신용거래설명서_20250324 | 없음 → SHA-256 대체 | PDF |
| 유진_반대매매안내(수집 20260805) | 없음 → SHA-256 대체 | HTML |

**수집 방안** — 각 사 공개 웹에 게시된 원문을 그대로 받는다. 파일별로 **원본 URL · 심사필 번호 · 개정일 · SHA-256 · 수집일**을 기록한다(`data/terms/README.md`).

**보존 방안** — 원문 바이트를 그대로 둔다. 텍스트 문서는 개행 정규화가 좌표를 어긋나게 하므로 `.gitattributes`의 `-text`로 막았다. 심사필 번호가 없는 문서는 **`content_sha256`이 버전 식별자**다.

⚠ **좌표는 추출기의 함수다.** 같은 PDF라도 추출기 버전이 다르면 문자 좌표가 달라진다. 그래서 추출기를 **정확한 버전으로 고정**하고, 올릴 때는 좌표를 다시 기록·검수한다.

### 5-2. 생성형 AI — 무엇을, 어떻게

**모델**: `claude-sonnet-5` (Anthropic Messages API). 비용 승인 상한 실행기가 이 모델 정가로 계산돼 있다.

**2패스 구조** — 인용 수집과 구조화를 분리한다.

```
1패스   document 블록에 citations: {enabled: true}
        → 응답이 cited_text 와 위치를 **네이티브로** 돌려준다
        (LLM 에게 좌표를 자가 보고시키지 않는다 — 그 경로는 거부한다)

2패스   1패스가 모은 인용문만 가지고 조건카드를 조립
        → JSON Schema + Pydantic 이중 검증
```

**프롬프트 캐싱** — 약관 본문을 캐시 프리픽스로 둔다(`cache_control: ephemeral, 5m`). 같은 문서 반복 호출의 입력 비용이 크게 떨어진다.

### 5-3. AI 출력에 거는 4중 방어 — 순서대로

```
①  모든 수치에 근거 좌표(페이지 + 스팬 + 인용)  →  좌표를 못 찾으면 카드 전체 거부
②  JSON Schema(jsonschema) + Pydantic 이중 검증
③  수치 범위 검사                                  r 1.0~2.0,  h 0~0.35
④  출력에 산식·계산이 섞이면 거부                 LLM 은 읽고 인용만 한다
```

### 5-4. 사람이 마지막에 선다 — `status`는 무조건 `draft`

AI가 만든 조건카드는 **예외 없이 `draft`** 로 나온다. `verified` 승격은 **사람이 원문과 대조한 뒤**에만 일어난다.

화면은 이 둘을 다르게 다룬다. `draft` 카드도 수량을 내지만 **배너로 그 사실을 말한다** — *"검수 전(draft) 조건카드. 아래 수치는 이 카드로 산출했습니다. 사람이 원문과 대조하기 전이므로 정식 판단의 근거로 쓰지 마세요."*

⚠ 이 배너는 원래 **그 카드를 정식 산출에 쓰지 않는다고 적혀 있었고, 거짓이었다.** 화면은 실제로 그 카드로 계산하고 있었다. 문구를 사실에 맞게 고쳤고, **같은 거짓 문장이 저장소 어디에도 다시 생기지 않도록 검사로 막았다** — 그 검사는 문구를 목록으로 들고 추적 파일 전체를 훑는다. (이 문서를 쓰면서 옛 문구를 그대로 인용했다가 그 검사에 걸렸다. 검사가 옳아서 문장을 바꿨다.) 근거 없는 안심을 주지 않는 것이 이 제품의 규율이라면, **근거 없는 면책도 같은 종류**다.

### 5-5. 데이터가 만드는 확장 재료

- **개정 diff** — 메리츠 구버전(25-125호)을 확보했다. 현행본을 나란히 두면 *"이번 개정으로 내 한계선이 어떻게 움직였나"* 의 실데이터가 된다.
- **교차 골든** — 신한 예시 계좌가 한투 사례와 같은 구조(투자원금 400만·융자 600만)다. 금융투자협회 공통 템플릿으로 보이며, **같은 계좌를 회사별 조건으로 돌리는** 검증 스위트를 만들 수 있다.
- **1차 사료로서의 공식** — 미래에셋 원문이 반대매매 수량 산식 자체를 공개한다. 우리 엔진 유도식의 독립 검증 근거다.

## 6. 기대 효과 및 확장 가능성*

### 6-1. 해결하는 문제와 기대 효과

| 지금 | 마진가드 이후 |
|---|---|
| 담보부족 통보를 받고 나서야 계산을 시작한다 | **통보 전에** 임계가를 알고 있다 |
| 약관에 있지만 내 숫자로 번역돼 있지 않다 | 보유수량·융자금을 넣으면 **가격 한 줄**로 나온다 |
| 해소 경로를 모르고 급하게 판다 | **입금 · 융자 상환 · 대용증권 · 자발적 매도** 네 경로의 금액을 함께 본다 |
| 회사마다 다른 조건을 비교할 방법이 없다 | 같은 계좌에 **조건만 갈아 끼운** 결과를 나란히 본다 |

**정량 예시** — 같은 담보부족액 300,000원에 대해:

```
현금 입금     300,000원
융자 상환     214,286원        입금보다 28.6% 적다
자발적 매도       96주         제비용 0.8% 가정
```

**융자 상환이 현금 입금보다 28.6% 적다**는 것은 약관에서 유도되는 사실인데, 통보 문자에는 적혀 있지 않다.

### 6-2. 실질적 혜택

**개인투자자** — 가장 큰 혜택은 *"내가 무엇을 모르는지 안다"* 는 것이다. 화면은 답이 없을 때 답이 없다고 말한다. 근거 좌표가 붙어 있으므로 **원문으로 직접 확인하러 갈 수 있다.**

**서비스 제공자(증권사)** — 담보부족 통보에 **조건 설명 링크**를 붙일 수 있다. 조건이 사전에 이해되면 통보 시점의 문의 부담과 분쟁 여지가 줄어든다. 조건카드 구조가 회사별로 분리돼 있어 자사 조건만 얹는 형태로도 쓸 수 있다.

### 6-3. 확장 가능성

**단계 1 — 폭 넓히기(문서)**: 지금 조건카드로 만든 것은 2사다. 원문은 7종 확보돼 있고 파이프라인은 같으므로, 회사를 늘리는 것은 **새 기능이 아니라 처리 건수**다.

**단계 2 — 축 늘리기(채널)**: 미수(결제 부족)는 신용과 다른 규칙으로 도는 별개 채널이고, 유진·신한 원문에 산식이 이미 확인돼 있다. 조건카드 스키마에 상품 축이 이미 있어 **같은 엔진으로 확장**된다.

**단계 3 — 시간 축(개정 diff)**: 약관은 개정되고, 개정은 사용자에게 통보되지 않는다. 판본을 나란히 두고 *"이번 개정으로 당신의 한계선이 8,400원에서 8,650원으로 올라갔다"* 를 보여주는 것은 **우리 구조에서만 자연스럽게 나온다** — 근거 좌표와 문서 해시가 이미 판본에 묶여 있기 때문이다.

**단계 4 — 실계좌 연동**: 지금은 **합성 계좌**다. 시세·잔고 프록시 경로(KIS OpenAPI)는 만들어 배포돼 있으나 **자격증명이 없어 동작하지 않는다** — 배포본에서 호출하면 `KIS_APP_KEY is required`가 돌아온다. 그리고 KIS 모의투자는 **신용거래를 지원하지 않아** 융자금·이자는 어차피 우리 장부여야 한다. 실계좌 축은 **연동 자체보다 신용 원장을 어디서 받느냐**가 남은 문제다.

### 6-4. 금융 서비스 밖으로

이 제품의 이전 가능한 자산은 반대매매 지식이 아니라 **"약관 → 검증 가능한 규칙 카드 → 결정론 계산"** 이라는 골격이다.

```
보험 약관        면책 조항 → 내 사고가 보장되는가
대출 약정        기한이익 상실 → 어느 조건에서 일시상환을 요구받는가
임대차 계약      갱신·해지 조건 → 내 계약이 언제 어떻게 끝나는가
통신·구독 약관   해지 위약금 산정
```

공통점은 셋이다 — **규칙이 문서에 있고**, **결과가 개인의 숫자로 결정되며**, **틀리면 되돌릴 수 없다.** 이 조건에서는 *"AI가 답을 만든다"* 보다 **"AI가 읽고, 근거를 붙이고, 계산은 검증 가능한 엔진이 한다"** 가 맞다.

## 7. 검증 방법과 한계 — 우리가 아직 못 하는 것

이 절을 자유 항목에 두는 이유는, **한계를 적는 것이 이 제품의 주장 자체**이기 때문이다. 모르는 것을 모른다고 말하는 서비스를 만든다면서 기획서에서 그러지 않으면 그 주장이 성립하지 않는다.

### 무엇으로 검증했나

| 축 | 방법 |
|---|---|
| 계산 | 증권사 원문의 계산 예시를 골든 케이스로 고정 — 엔진 출력이 원문 예시와 일치해야 통과 |
| 근거 | 매번 원문을 다시 파싱해 좌표·해시·인용문을 대조 |
| 화면 | 브라우저 자동화(Chromium · Firefox · 375px)로 실제 렌더 확인 |
| 의존성 | 상류 릴리스가 결과를 바꾸면 CI가 즉시 빨간불 — 실제로 두 번 작동했다 |

### 지금 못 하는 것 — 숨기지 않는다

- **심사 URL에서 임의 약관 업로드는 되지 않는다.** 인제스트 파이프라인은 저장소 안에서 동작하고 테스트도 있으나, **배포돼 있지 않다.** 심사자가 보는 화면은 사전 계산된 조건카드만 쓴다.
- **조건카드로 만든 회사는 2사**(한국투자·메리츠)다. 원문 7종은 확보돼 있으나 유료 종단으로 카드를 생성한 것은 한국투자 1종이다.
- **사파리(WebKit)는 확인하지 않았다.** Chromium·Firefox·375px만 실측했다.
- **비율을 가르는 축이 인용 스팬 밖에 있는 문서는 지원하지 않는다**(메리츠 유형). 이것은 결함이 아니라 **선택**이지만, 지원 범위가 좁아지는 것은 사실이다.
- **날짜 판정이 열람 시각(브라우저 시계) 기준**이다. 시계를 바꾸면 신선도 표시가 달라진다 — 보안 경계가 아니라 표시 규약이다.
- **실계좌·시세 연동은 배포본에서 동작하지 않는다.** 프록시 경로는 있으나 자격증명이 없다(`KIS_APP_KEY is required`). 화면의 계좌는 **합성 계좌**다.

전체 목록과 재현 절차는 **첨부2 §5(MVP 검증 방법)** 에 있다.
